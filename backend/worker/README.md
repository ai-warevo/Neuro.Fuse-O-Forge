# 🛠 Universal Worker (Data Plane)
Роль: Исполнитель задач. Находится в бесконечном цикле, держит модели «прогретыми» и выполняет генерацию контента.

## Стек и окружение
* Язык: Python 3.10.
* ML Core: PyTorch + специализированные библиотеки (diffusers, transformers, audiocraft).
* Broker: redis-py (синхронный клиент).
* Hardware: GPUtil для мониторинга видеокарты.
* Контекст: Работает внутри Docker-контейнера с проброшенным GPU (NVIDIA Container Toolkit).

## Жизненный цикл воркера
### Инициализация (Startup)

   1. Считывает переменную окружения FORGE_TYPE (определяет роль: IMAGE, SOUND, TEXT или UI).
   2. Загружает дефолтную модель для своего типа в VRAM (настройки берутся из config.yaml).
   3. Регистрирует себя в Redis, создавая ключ worker_health:{type}:{hostname}.

### Работа с очередью (Consumer Loop)

   1. Подключается к Redis Stream forge:tasks:{type}.
   2. Входит в группу потребителей worker_group (для исключения дублирования задач).
   3. Использует команду XREADGROUP для получения новой задачи.
   4. После получения задачи переходит в статус Busy.

### Логика Hot Swap (Смена моделей)
Если в задаче поле model_name не равно auto и не совпадает с текущей загруженной моделью:

   1. Проверяет наличие запрошенной модели в локальном хранилище.
   2. Полностью выгружает текущую модель: del self.model, torch.cuda.empty_cache().
   3. Загружает новую модель. Если загрузка невозможна — шлет статус ERROR.

### Выполнение (Forge Process)

   1. Начало: Публикует в Pub/Sub канал logs:{task_id} сообщение: {"type": "log", "msg": "Generation started"}.
   2. Прогресс: Если пайплайн нейросети поддерживает callback, воркер шлет сообщения: {"type": "progress", "value": X}.
   3. Генерация: Выполняет расчеты (диффузия, инференс текста и т.д.).
   4. Сохранение: Записывает результат в папку /app/output/{type}/{task_id}.ext.

### Завершение и ACK

   1. Публикует финальное сообщение: {"type": "success", "url": "/files/{type}/{task_id}.ext", "bench": 12.3}.
   2. Отправляет сигнал XACK в Redis Stream, подтверждая выполнение задачи.
   3. Переходит в статус Idle, готовый к новой задаче.

## Обработка исключений

* Out of Memory (OOM): Воркер должен перехватить ошибку torch.cuda.OutOfMemoryError, отправить статус ERROR, вызвать empty_cache() и продолжить работу.
* Timeout: Если генерация длится дольше лимита, установленного в конфиге, воркер должен прервать процесс и отдать ошибку.

## Фоновый мониторинг (Heartbeat)
Воркер запускает отдельный поток (Thread), который раз в 10 секунд обновляет статус в Redis:

* Ключ: worker_health:{FORGE_TYPE}:{hostname}.
* Данные:

```json
{
  "status": "idle | busy",
  "vram_free": "MB",
  "gpu_load": "%",
  "temperature": "C",
  "current_model": "name"
}
```

* TTL: 15 секунд (если воркер «умрет», данные исчезнут сами).

## 5. Специфика параметров (params)
Воркер обязан строго соблюдать типы данных из params, переданных API:

* Приводить seed к int.
* Приводить guidance_scale к float.
* Масштабировать width/height под требования модели (кратность 8).
